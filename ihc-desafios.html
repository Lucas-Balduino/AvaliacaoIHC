01
Navegabilidade

Melhoria de Interface
em Sistema de Folha de Pagamento

🔴 Problema
Um sistema de folha de pagamento crítico estava recebendo duras críticas dos clientes por dificuldade de compreensão do fluxo, baixa conversão (usuários abandonavam no meio do processo) e erros de usabilidade que prejudicavam a navegação. O conceito de navegabilidade — a facilidade de percorrer as opções sem se sentir perdido — estava sendo violado em múltiplos pontos.
🎨
Cores de Alto Impacto nos Textos
O título e a mensagem de alerta usavam cores muito impactantes, prejudicando a leitura. Cores usadas desproporcionalmente perdem o papel de chamar atenção para pontos importantes.
🔄
Ordem Invertida dos Botões
O botão "Avançar" aparecia à esquerda e "Retornar" à direita — o inverso do padrão. Isso contraria a leitura natural (esquerda→direita) e a convenção estabelecida dos sistemas.
❓
Ausência de Ícones de Ajuda
Sem ícones de ajuda (?) no sistema, o usuário que não conseguia realizar uma entrada de dados ficava sem orientação e tendia a abandonar o software por falta de suporte contextual.

✦ Resultado das Melhorias

ANTES — Interface Original
DEPOIS — Interface Melhorada
✅
Cores Funcionais e Semânticas
Cores aplicadas com propósito: vermelho para cancelar/perigo, verde para confirmar/avançar — seguindo as convenções semióticas que os usuários já reconhecem intuitivamente.
✅
Ordem Corrigida dos Botões
"Cancelar" à esquerda e "Avançar" à direita, seguindo o padrão universal de interfaces. O texto também foi atualizado para ser mais específico e contextual.
✅
Mensagem Mais Clara e Objetiva
A mensagem foi reescrita para identificar o usuário afetado ("Confirma a exclusão do usuário 'João'?"), tornando a ação mais específica e compreensível.
02
Acessibilidade

Interface para
Usuários com Deficiência Visual

🔴 Cenário
A equipe de design precisa criar um artefato gerenciador de cursos internos para funcionários da área de treinamento de uma empresa cliente. O desafio: todos os usuários são deficientes visuais, e essa limitação não deve de forma alguma impedir o uso normal da ferramenta. Qual tipo de interface e equipamento devem ser usados?
A
a) Qual tipo de interface?
A melhor escolha é a interface orientada à fala. Por ser baseada em comandos de voz e saída de áudio, ela se adapta naturalmente às necessidades de usuários com deficiência visual, eliminando a dependência de elementos gráficos como botões, menus visuais e texto na tela para operação do sistema.
B
b) Que equipamento utilizar?
Os designers deverão utilizar leitores de tela. Com esse equipamento, os usuários com deficiência visual conseguem ouvir o conteúdo exibido e verificar o que foi digitado, além de identificar quais objetos manipularam — como botões e itens de menu — com total autonomia.
💡 Princípio de Design
Com o avanço da tecnologia, as interfaces não devem apenas atingir seus objetivos funcionais — elas devem se adaptar aos usuários que as utilizam. Projetar para acessibilidade não é uma limitação, é uma expansão do design: ao criar para casos extremos, tornamos a experiência melhor para todos.
03
Processo de Design

Projetando para Ricardo:
Solução Computacional Assistiva

📋 Caso de Estudo
Ricardo

Usuário que está perdendo a visão gradativamente e é apaixonado por tecnologia.

⌚ Relógios inteligentes 📱 Smartphones 🏠 Sensores residenciais

Ricardo enfrenta dificuldade crescente para se locomover em ambientes desconhecidos devido à perda progressiva de visão. Ele contratou a empresa Desenvolve! para criar uma solução computacional que o auxilie nessa tarefa. A equipe ainda não tem conhecimento do domínio da aplicação.

Passo a Passo do Processo de Design

Fase 01 — Compreensão
Entender o Usuário e o Problema
A primeira atividade é usar técnicas para compreender o perfil do usuário, suas tarefas, necessidades, sentimentos e o que deseja. Como a equipe não conhece o domínio, esse mapeamento é essencial antes de qualquer proposta de solução.
Storytelling Picture Cards Jornada do Usuário
Fase 02 — Exploração
Explorar Possíveis Soluções
Com o problema compreendido, a criatividade da equipe é mobilizada para explorar diferentes abordagens. Storyboards permitem visualizar cada proposta em seu contexto real de uso, identificando pontos positivos e negativos antes de qualquer desenvolvimento. Exemplos investigados: bengala com sensores, relógio com câmera, óculos inteligentes.
Storyboards Ideação Análise de Cenários
Fase 03 — Iteração
Amadurecimento Iterativo da Proposta
As atividades das fases anteriores são realizadas múltiplas vezes. Nessa etapa, ainda não há nada concreto — as técnicas auxiliam no amadurecimento da solução, investigando possibilidades, identificando problemas potenciais e pontos de investigação, até que a proposta seja aprovada pela equipe e por Ricardo.
Revisão Iterativa Co-criação com Usuário
Fase 04 — Prototipagem
Protótipos e Validação
Antes de codificar, protótipos (começando com baixa fidelidade) são desenhados para validação com Ricardo. Com os protótipos é possível concretizar a proposta e avaliá-la na prática: se houver problemas ou pontos de melhoria, ajustes são feitos antes do desenvolvimento final.
Protótipo Baixa Fidelidade Teste com Usuário Refinamento
💡 Insight do Processo
Essas técnicas auxiliam o designer a criar contextos de uso, conhecer usuários e atividades, entender a tecnologia disponível, organizar informações e apresentar vantagens e desvantagens das propostas. Elas abrem o processo criativo para novas possibilidades — sem nunca pular direto para a codificação antes da validação com o usuário real.

TypeScript · Programação Orientada a Objetos

Modelagem de Sistema
de Vendas Online

🔴 Contexto
Com o crescimento das vendas pela internet, sistemas web precisam modelar entidades do mundo real em estruturas digitais. Usando TypeScript (linguagem orientada a objetos), o desafio é modelar as classes Produto e Venda para um sistema de e-commerce, com um exemplo de utilização completo.
// a) Classe que representa um Produto no sistema de vendas class Produto { id: number; nome: string; descricao: string; valor: number; fabricante: string; }
// b) Classe que representa uma Venda (composta por múltiplos Produtos) class Venda { constructor(produtos: Array<Produto>) { this.produtos = produtos; } produtos: Array<Produto>; valorVenda() { let soma = 0; for (let produto of this.produtos) { soma = soma + produto.valor; } alert("O valor total da venda é: " + soma); } }
// c) Exemplo de utilização: instanciando Produtos e criando uma Venda let produtos = new Array<Produto>(); let produto1 = new Produto(); produto1.id = 1; produto1.nome = "Cadeira presidente"; produto1.descricao = "Cadeira muito confortável para ser usada no escritório."; produto1.valor = 499.99; produto1.fabricante = "Fábrica Brasil"; let produto2 = new Produto(); produto2.id = 2; produto2.nome = "Mouse sem fio"; produto2.descricao = "Mouse sem fio da marca Brasil com o máximo de desempenho."; produto2.valor = 20; produto2.fabricante = "Fábrica Brasil"; produtos.push(produto1); produtos.push(produto2); let venda = new Venda(produtos); venda.valorVenda(); // Alert: "O valor total da venda é: 519.99"
💡 Conceito de OO
As classes na programação orientada a objetos são abstrações do mundo real. A classe Produto modela um item comercial com seus atributos característicos, enquanto Venda encapsula uma transação comercial e o comportamento de calcular o valor total — demonstrando composição de objetos e encapsulamento de lógica de negócio.
